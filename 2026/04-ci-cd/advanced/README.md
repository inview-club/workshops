## Задание 1. Настройка GitLab Runner

Напишите Docker Compose для запуска GitLab Runner, зарегистрируйте его в своём проекте и настройте.

### Требования

- Имя Runner — уникальное для вашей команды.
- Executor — `docker`.
- Общий лимит одновременно выполняемых jobs — `2`.
- Образ по умолчанию — `docker:27.5.1`.
- Привилегированный режим — выключен.
- Контейнер Runner имеет доступ к Docker daemon хоста.
- Job-контейнеры могут использовать Docker daemon хоста для сборки образов.
- Runner может выполнять jobs только с тегом `docker`.

Все настройки пропишите в конфигурационном файле config.toml.

### Проверка

1. Запустите Runner через Docker Compose.
2. Убедитесь, что Runner отображается в GitLab как доступный.
3. Запустите тестовый pipeline.
4. Проверьте, что job выполняется на вашем Runner.

### Результат

Runner доступен в GitLab и успешно выполняет тестовую job.

> Доступ к Docker socket хоста даёт широкие полномочия. Используйте эту конфигурацию только на выделенном учебном хосте и не запускайте недоверенный код.

## Задание 2. Исправление pipeline

В репозитории настроен pipeline проверки и сборки Go-приложения. Конфигурация содержит намеренные ошибки и антипаттерны.

Ваша задача — исправить pipeline и объяснить внесённые изменения.

### Что нужно сделать

1. Изучите `.gitlab-ci.yml` и команды работы с приложением.
2. Исправьте условия создания pipeline и запуска jobs.
3. Исключите дублирующиеся branch- и merge request-pipeline для одного изменения.
4. Перестройте порядок выполнения и зависимости:
   - независимые проверки должны выполняться параллельно;
   - сборка и публикация образа должны запускаться только после успешных обязательных проверок.
5. Убедитесь, что замечания линтера и упавшие тесты приводят к ошибке соответствующей job.
6. Настройте генерацию и публикацию отчётов:
   - JUnit — для результатов тестирования;
   - Code Quality — для замечаний линтера.
9. Создайте Merge Request с исправлениями.

В описании MR кратко перечислите найденные проблемы и объясните решения.

### Сценарии проверки

Проверьте как минимум следующие случаи:

- Все обязательные проверки проходят — образ публикуется.
- Тест падает — образ не публикуется.
- Линтер находит замечания — образ не публикуется.
- Для ветки с открытым MR не создаются дублирующиеся pipeline.
- Результаты тестов и статического анализа доступны в интерфейсе GitLab.

### Подсказки

- Разделяйте условия создания pipeline и условия включения jobs.
- Проверяйте не только порядок stages, но и явные зависимости между jobs.
- Файл отчёта сначала нужно создать, затем передать GitLab.
- Публикация отчёта сама по себе не делает проверку блокирующей.
- Способ Docker-сборки должен соответствовать конфигурации Runner.

### Результат

Merge Request с исправленным pipeline, обоснованными зависимостями и опубликованными отчётами проверок.

## Задание 3. Автоматизация релиза

Добавьте в исправленный pipeline выпуск релиза приложения.

### Что нужно сделать

Создайте jobs для:

1. Добавьте обязательную проверку в pipeline Merge Request: версия в `VERSION` должна быть выше версии в `main`. Если версия не обновлена, проверка должна блокировать слияние MR.
2. Добавьте ручную job создания Git-тега по версии из `VERSION`, доступную только в pipeline ветки `main`.
3. Настройте запуск отдельного релизного pipeline при создании тега.
4. В релизном pipeline проверьте совпадение версии тега и содержимого `VERSION`, запустите обязательные проверки кода и тесты.
5. После успешных проверок соберите и опубликуйте Docker-образ с релизной версией.
6. Сгенерируйте `CHANGELOG.md` по истории изменений.
7. Создайте релиз в GitLab для существующего тега, используя CHANGELOG как описание.

Релиз запускается вручную из pipeline основной ветки после успешного прохождения обязательных проверок.

### Правила версионирования

- Источник версии релиза — файл `VERSION`.
- Файл содержит одну строку с версией, например `1.4.2`.
- Релизный Docker-образ получает тег с версией из `VERSION`.
- Нерелизный образ получает тег по хэшу коммита.
- Git-тег и релизный образ должны обозначать одну и ту же версию.

### Проверка

- Версия читается из `VERSION`, а не дублируется в конфигурации jobs.
- Образ с релизной версией опубликован в Container Registry.
- Git-тег указывает на коммит, из которого собран релизный образ.
- В GitLab создан релиз с описанием изменений.
- Создание Git-тега не запускает повторный выпуск того же релиза.

### Результат

В GitLab создан релиз и Git-тег, а в Container Registry опубликован образ соответствующей версии.
